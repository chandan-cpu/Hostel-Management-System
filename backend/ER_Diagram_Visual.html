🔗 Relationship Legend

USER → ROOM: One-to-Many (Optional) - A user can occupy multiple rooms over time
STUDENT → ROOM: Many-to-One (Optional) - Multiple students can be assigned to same room
BOOKING → PAYMENT: One-to-Many - Each booking can have multiple monthly payments
STUDENT → BOOKING: One-to-Many (Logical) - Students can make multiple bookings

👤 USER Entity

_id (ObjectId) - Primary Key
name (String) - Full name
email (String) - Unique email
password (String) - Hashed password
phoneNumber (Number) - Contact
enrollmentNumber (String) - Student ID
department (String) - Academic dept
yearOfStudy (String) - Current year
isVerified (Boolean) - Email verified
tokenExpiry (Date) - Reset token expiry

🎓 STUDENT Entity

_id (ObjectId) - Primary Key
name (String) - Student name
email (String) - Unique email
phone (String) - Contact number
avatar (String) - Profile picture URL
year (String) - Academic year
course (String) - Course of study
room (String) - Assigned room
status (String) - Current status
dues (Number) - Outstanding amount

🏠 ROOM Entity

_id (ObjectId) - Primary Key

capacity (Number) - Max occupancy

status (String) - Availability

📝 BOOKING Entity

duration (String) - Stay duration
status (String) - Booking status

💰 PAYMENT Entity

_id (ObjectId) - Primary Key

month (String) - Payment month
dueDate (Date) - Due date
paidDate (Date) - Payment date

📊 Business Rules

Room Assignment: Students are assigned rooms based on capacity and preference
Payment Generation: Monthly payments are auto-generated for confirmed bookings
Status Management: Booking and payment statuses control the workflow
Data Integrity: Foreign key relationships maintain data consistency
